# Find a group starting from one primitive operation

In the [single-hint experiment](../FOLD-PLACEMENT-20261115-001/preregistration.md), named and flat searches made the same semantic placements and gave substantially different elapsed times on a busy host. The named blind arm missed the screen. Its informed version met it. This bounded successor tests the indicated missing step at the same width. All data for this new measurement remain unseen at design time. Its labels and stream order change; its mathematical functions up to renaming are deliberately the same.

An innermost copy of the relevant operation contains an ordinary binary gate. For an exact AND of two operands, fixing them at 00, 01 and 10 leaves the same function of all remaining operands. The fourth residual may differ. OR and XOR have their own equality patterns. A solver can therefore look for a valid pair first. It can compute that one bit and continue, or test each remaining operand as a possible third for the library function. A found pair remains usable when every attempt to extend it fails. Every check, failed extension and residual construction is charged. A correct returned program can contain a different grouping from the generating tree.

The primitive pair-only solver knows AND, OR and XOR. Compare it to guiding the same pair search with F and rebuilding the local answer from ordinary gates, using the verified six-NAND call, or emitting the same operation fully inlined. The earlier blind triple primitive/named/flat methods and the unwrapped direct primitive are additional controls. Public inputs contain only opaque rule IDs for accounting, arity and the truth table. The engine receives only the truth table. Each method owns its cache, and each repeat starts empty. The checker evaluates all 512 assignments to the original inputs.

Run each method in a fresh shared-runner worker. One worker is active at a time. Pin each to the same CPU when the OS supports affinity. Rotate and reverse/reorder method streams so that each takes each position once in eight paired warm blocks. Hold the order of the 48 rules fixed in every stream. Two cold repeats with one fresh engine per task test sensitivity. Count setup and code/library loading inside the worker, physical construction, searching, checking and serialization of the return. Exclude scientific trace output, runner overhead and the common generation of the benchmark. Record CPU as well as elapsed time; the first study's elapsed-time spread is the reason for designating process CPU as the primary endpoint here.

Use the lowest median warm CPU among the unwrapped direct primitives, earlier blind triple primitives and new atomic pair-only solver as the no-library benchmark. The preselected primary candidate is the pair-guided named fold. Proceed to a separate paid selection study only if its entire mixed stream is exact, its median total CPU is at least 10% lower than the benchmark, it wins at least six of eight paired CPU comparisons, its median elapsed time is lower, and its within-stream CPU excluding module loading also falls. Its matched inline route must have identical semantic placements and must improve marginal CPU over the same no-library benchmark. Identify a likely implementation/ordering effect if the guided primitive reconstruction also wins. Print the measured amounts whichever stopping rule fires, and compare the atomic locator to its older triple baseline. A primitive-only improvement earns no deeper fold run.
